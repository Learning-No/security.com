S · Spoofing

Can an identity or service be impersonated? Review MFA, certificates, and workload identity.

Explore threat guidance

What to examine

User, administrator, device, service, and workload identities; sign-in flows; session tokens; certificate trust.

Example scenarios

  • A stolen account is used to access an internal application.
  • A service accepts an untrusted or incorrectly validated identity.
  • A session remains valid after an account is disabled.

Defensive controls

  • Use MFA, preferably phishing-resistant for privileged access.
  • Validate issuer, audience, expiry, and signature of tokens; validate certificates.
  • Use managed workload identities and short-lived credentials.
  • Revoke sessions promptly and monitor unusual sign-in patterns.

Evidence to collect

MFA coverage, identity configuration, token-validation tests, certificate inventory, access logs, and session-revocation test results.

Review questions

Which identities can access this component? How is identity proof verified? How quickly can compromised access be revoked?

T · Tampering

Can data or configuration be changed without authorisation? Review integrity and change control.

Explore threat guidance

What to examine

Stored records, messages, files, software packages, deployment pipelines, infrastructure configuration, and audit settings.

Example scenarios

  • An unauthorised change alters a customer record or transaction.
  • A deployment artifact or dependency is replaced before release.
  • A configuration change weakens a security control without approval.

Defensive controls

  • Enforce server-side authorisation and input validation for every sensitive change.
  • Use integrity checks, signed artifacts, and trusted build pipelines.
  • Apply version control, peer review, approvals, and configuration-drift monitoring.
  • Protect backups and logs against unauthorised modification.

Evidence to collect

Change tickets, code reviews, artifact signatures, integrity alerts, access records, and configuration-drift reports.

Review questions

Who can modify this asset? Are changes attributable and approved? Can unauthorised modifications be detected and recovered?

R · Repudiation

Can an action be denied? Review attributable, protected audit records.

Explore threat guidance

What to examine

Authentication events, administrative actions, transactions, API calls, approvals, and system-to-system activity.

Example scenarios

  • A privileged change has no reliable record of who initiated it.
  • Several people share one account, making actions difficult to attribute.
  • Logs can be edited or deleted by the same account being monitored.

Defensive controls

  • Use unique identities and avoid shared administrator accounts.
  • Record actor, action, target, timestamp, result, and relevant correlation ID.
  • Synchronise clocks and centralise logs with restricted write access.
  • Set retention, integrity protection, alerting, and documented review procedures.

Evidence to collect

Sample audit events, time-synchronisation status, log access policy, retention settings, and audit-integrity test results.

Review questions

Can an important action be traced to an individual or service? Are records complete, time-aligned, retained, and protected?

I · Information disclosure

Can sensitive data be exposed? Review access, encryption, and data flows.

Explore threat guidance

What to examine

Personal and business data, API responses, object storage, databases, backups, logs, exports, and third-party data flows.

Example scenarios

  • An API returns another user's records because object-level access checks are missing.
  • A storage location is accessible more broadly than intended.
  • Sensitive values appear in application logs or error messages.

Defensive controls

  • Classify data and enforce least-privilege access at every layer.
  • Encrypt data in transit and at rest; manage keys separately from protected data.
  • Minimise collection, mask sensitive values, and apply retention and disposal rules.
  • Test tenant isolation, API authorisation, sharing permissions, and backup access.

Evidence to collect

Data-flow diagrams, classification register, access reviews, encryption configuration, API test results, and data-retention records.

Review questions

What sensitive data exists and where does it flow? Who can access it? Could responses, logs, backups, or exports reveal more than intended?

D · Denial of service

Can availability be disrupted? Review capacity, rate limits, and resilience.

Explore threat guidance

What to examine

Public endpoints, authentication services, application queues, databases, shared dependencies, quotas, and recovery arrangements.

Example scenarios

  • A sudden traffic spike exhausts application or database capacity.
  • Expensive requests consume resources and delay normal users.
  • A single dependency failure makes several services unavailable.

Defensive controls

  • Set sensible request limits, quotas, timeouts, and queue bounds.
  • Use load balancing, caching, autoscaling safeguards, and upstream traffic protection.
  • Isolate critical dependencies and define graceful degradation behavior.
  • Monitor service health and rehearse recovery using authorised load tests.

Evidence to collect

Capacity forecasts, service-level objectives, rate-limit configuration, availability dashboards, incident records, and recovery exercise results.

Review questions

What resource is the bottleneck? Which users or services are affected by a dependency failure? How is service restored and prioritised?

E · Elevation of privilege

Can a user gain excess permissions? Review authorisation and privilege boundaries.

Explore threat guidance

What to examine

Role and permission models, administrative functions, service permissions, tenant boundaries, trust relationships, and privileged workflows.

Example scenarios

  • A standard user can invoke an administrator-only function.
  • A user changes an object identifier to access another user's resource.
  • A workload has broad permissions beyond its required task.

Defensive controls

  • Enforce server-side authorisation on every action and object.
  • Use least privilege, scoped roles, separation of duties, and just-in-time elevation.
  • Validate tenant and ownership boundaries; do not rely on hidden UI controls.
  • Review privileged assignments and test negative access cases.

Evidence to collect

Role matrix, permission reviews, authorisation test cases, privileged-access logs, and service-account permission inventories.

Review questions

Can a lower-privileged identity perform a higher-privileged action? Are object and tenant boundaries checked on the server? Are elevated rights time-limited and reviewed?

Controls library

Baseline security control families and the evidence that demonstrates operation.

Identity & access
MFA: Require phishing-resistant MFA for privileged and sensitive access where feasible.
Least privilege: Use role-based access, scoped permissions, and periodic access reviews.
PAM: Control privileged sessions, approvals, and credential rotation.
Lifecycle: Automate joiner, mover, and leaver access changes.
Network & infrastructure
Segmentation: Separate user, application, data, management, and production zones.
Secure configuration: Apply hardened baselines and configuration drift checks.
Exposure management: Inventory assets and prioritise remediation by risk.
Resilience: Protect backups and test recovery procedures.
Application & data
Secure SDLC: Threat model, review code, scan dependencies, and test before release.
API security: Enforce authentication, object-level authorisation, validation, and rate limits.
Encryption: Protect data in transit and at rest with managed keys.
Secrets: Keep secrets out of source code and rotate them through a vault.
Detection & governance
Logging: Collect time-synchronised security events with controlled retention.
Detection: Map use cases to threats and test alert quality.
Incident response: Define roles, escalation, evidence handling, and exercises.
Assurance: Track exceptions, owners, evidence, and review dates.
